# Merchant screen parity matrix

This matrix maps every Stitch reference in `screens/MerchantScreens/` to its Flutter route or state. For each one it records the current differences, the required work and the status. It is the working tracker for the Merchant UI parity pass and is updated batch by batch.

- **Coverage:** 75 screen folders, the root pair (`screens/MerchantScreens/screen.png` + `code.html`, the Arabic add-product form) and `speedygo_merchant_system/` (only `DESIGN.md`, the token source). Each folder's detailed analysis (design, Flutter mapping, differences, contract, alternatives, required work) is linked in the last column and lives in `../audit/parity/inventory/`.
- **Comparisons:** see `../audit/parity/COMPARISON_INDEX.md`.
- **Sample data:** reference names, amounts, timers and statuses are example data. They are never hardcoded; fixture captures use equivalent representative data.
- **Visual acceptance:** "done (mocked compared)" means implemented and compared side by side by the implementer. It is **not** visual acceptance, which belongs to the product owner (`human_accepted`).

## Status vocabulary

| Status | Meaning |
| --- | --- |
| `needs_work` | Supported by existing contracts; visual or behaviour work required. |
| `partial_contract_limited` | Implementable except for elements with no backend contract, which are omitted (never faked). |
| `blocked_contract` | The screen's core purpose needs a contract that does not exist. Proposal in the gaps section. |
| `not_applicable_duplicate` | Same state as a canonical reference, or merged by a documented decision. |
| `exception_approved` | Covered by a previously agreed exception (`MERCHANT_UI_SOURCE_OF_TRUTH.md` §3/§7). |
| `exception_approved*` | Exception for server-authoritative *state* only; visuals follow the reference (D-G1 decided). |

The **Progress** column records the parity-pass result: `—` (not started), `done (mocked compared)`, `partial (see gaps)`, `no change (blocked)`, `no change (exception)`.

**Delay reasons: existing API versus a future contract.** The tiles use the existing estimate-revision API unchanged, putting their label text into its optional free-text `reason` (max 255). The support topic tiles work the same way: they produce message text, not a ticket category.

**Variants and extras: save model (explicit UX difference, not changed).** Today every confirmed group or option sheet, delete and availability switch calls the API immediately (`option_groups_screen.dart`), and the list reloads after each call. The references end with "Enregistrer les variantes" / "Enregistrer les suppléments". A decorative Save button over immediate saves would mislead, so none was added. The backend has only per-item endpoints (POST/PATCH/DELETE for groups and options), with no batch or transaction. Proposed behaviour, for your decision before any persistence change:
1. **Draft:** confirming a sheet, deleting or toggling availability changes a local draft only. Changed items are marked "Modifié" or "Nouveau", and deleted items are struck through with an "Annuler" link. The customer preview reads the draft.
2. **Save:** a sticky "Enregistrer les variantes" (or "suppléments") button is enabled only when the draft differs from the last server state. It sends deletes, then updates, then creates, one at a time, in display order.
3. **Partial failure:** the calls are sequential and not atomic, so a failure can leave some changes saved and others not. On the first error the save stops. The screen must not reload and replace the draft: every unsaved edit, including the one that failed, stays in the draft and stays marked. Only the changes the server confirmed are folded into the new baseline, from each successful response. A server refresh may update items the merchant has not edited, but never overwrites an edited one; a conflict (for example a 409 on an item changed elsewhere) is shown on that item for the merchant to resolve. The message says how many changes were saved and which item failed (for example a group still below its minimum). Retrying sends only what is still unsaved.
4. **Leaving with unsaved changes:** back or swipe asks "Quitter sans enregistrer ?" with Rester / Quitter. Nothing is persisted locally across app restarts.
5. **Roles:** unchanged (OWNER/MANAGER edit; STAFF read-only).

The alternative is to keep immediate save and show "Enregistré" feedback per change. Both are client-only; a truly atomic save would need a batch endpoint.

### Terms and declaration contract (proposal, D-G5)

Not implemented. No legal text is written here; the texts must come from SpeedyGo legal/product and are referenced by version only.

- **Versioned documents (backend-owned):** `GET /api/v1/merchant/legal/current` returns the documents a merchant must accept, e.g. `[{ "kind": "MERCHANT_TERMS", "version": "2026-10-01", "url": "…", "sha256": "…" }, { "kind": "DOSSIER_ACCURACY_DECLARATION", "version": "…", "url": "…" }]`. The client shows exactly what it receives.
- **Acceptance on submission:** `POST /api/v1/merchant/:merchantId/verification/submit` gains `{ "acceptances": [{ "kind": "MERCHANT_TERMS", "version": "2026-10-01" }, { "kind": "DOSSIER_ACCURACY_DECLARATION", "version": "…" }] }`. The server rejects the submission (`LEGAL_ACCEPTANCE_REQUIRED` / `LEGAL_VERSION_OUTDATED`) unless every required current version is present.
- **Persistence (append-only, immutable):** one row per acceptance: merchant, accepting account and membership role, document kind and version, the verification submission it belongs to, and `acceptedAt` **recorded by the server clock** (never taken from the client), plus request metadata the backend already records for audit (device/session reference). Resubmission after a rejection records new rows; old rows are never updated.
- **Read-back:** the merchant `me`/verification summary exposes `legalAcceptance: { termsVersion, declarationVersion, acceptedAt }` so the review screen can show "Accepté le …" and the admin dossier can show who accepted which version and when.
- **Version change:** when a new terms version is published, existing merchants are asked to accept it on next launch (separate from verification); the older acceptance stays on record.
- **Schema sequence:** this needs a domain-model entry, then the ERD, then the Prisma contract (workspace rule); no table is added before that.
- **Client:** only then do the registration consent and review declaration checkboxes appear, disabled submit until ticked, and the stored `acceptedAt` is displayed from the server.
